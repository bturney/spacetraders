A health request through Phoenix

Follow the smallest complete HTTP path in this application before you study the dashboard.

The path

GET /health
    |
    v
Router: :api pipeline, HealthController.show/2
    |
    v
Controller: json(conn, %{status: "ok"})
    |
    v
HTTP 200 {"status":"ok"}

lib/spacetraders_web/router.ex:16-24 creates the :api pipeline, accepts JSON, and routes GET /health to HealthController.show/2. The slash and verb select the endpoint; :show selects the function.

Why show/2?

Elixir names a function by its module, name, and arity. show/2 means the function named show takes two arguments:

def show(conn, _params) do
  json(conn, %{status: "ok"})
end

conn is the request/response value threaded through Plug and Phoenix. _params means the function receives route/query parameters but deliberately does not use them. The leading underscore avoids an unused-variable warning.

The executable specification

The controller test makes the HTTP contract precise:

test "GET /health responds 200 with status ok", %{conn: conn} do
  conn = get(conn, ~p"/health")
  assert json_response(conn, 200) == %{"status" => "ok"}
end

~p"/health" is Phoenix's verified-route sigil. It checks the route against the router at compile time. Unlike a generic string, a stale route is caught before deployment.

Practice: run the exact test

source scripts/_toolchain.sh
mix test test/spacetraders_web/controllers/health_controller_test.exs

Expected result: one test, zero failures. This does not need the running application or a game token. Read the test output before moving on.

Which file decides that GET /health invokes HealthController.show/2?

The router maps an HTTP method and path to a controller action. The test checks that the resulting behavior matches the contract.

Primary source: Phoenix request lifecycle. Repository files: lib/spacetraders_web/router.ex, lib/spacetraders_web/controllers/health_controller.ex, and its test.
