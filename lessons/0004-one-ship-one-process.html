One Ship, one process

The application uses a GenServer for each active Ship because arrival and Cooldown timers are independent, stateful, and must recover after application restart.

The relevant supervision tree

SpaceTraders.Supervisor
    |
    +-- Registry: ShipRegistry
    +-- DynamicSupervisor: ShipSupervisor
             |
             +-- ShipServer for ORBITALIST-1
             +-- ShipServer for ORBITALIST-2
             +-- ...

SpaceTraders.Application.start/2 starts the Registry and DynamicSupervisor. A DynamicSupervisor accepts new children at runtime, so a ShipServer exists only when a Ship needs one. This is closer to Go actors managed by a fault-tolerant runtime than to a fixed Java executor pool.

What the ShipServer owns

SpaceTraders.Fleet.ShipServer owns only in-memory waiting state for one Ship: arrival and Cooldown timers. Durable Timeline events live in SQLite. On startup, init/1 reads pending events and re-arms timers. When a timer fires, it fetches authoritative Ship state from the game before unblocking the Ship.

def handle_info({:timeline, %Event{} = event}, state) do
  type = String.to_existing_atom(event.event_type)

  if not Timeline.pending?(event) do
    {:noreply, drop_pending_event(state, type, event)}
  else
    handle_pending_event(type, event, state)
  end
end

The callback receives its own scheduled message. It returns {:noreply, state}: do not send a synchronous reply; keep running with this next immutable state value.

Why not trust a timer?

The game is authoritative. A local timer might expire while the game still reports IN_TRANSIT because of clock skew or stale state. The ShipServer re-pulls the Ship and retries rather than allowing an action known to fail. This preserves the project's game-truth rule.

Then read the test named "does not unblock while the game still reports the ship in transit". It tests a time-sensitive concurrent behavior without talking to the real game API.

Why does a ShipServer refresh the Ship after an arrival timer fires?

The timer is a local scheduling hint. The SpaceTraders game decides whether the Ship is truly no longer in transit or on Cooldown.
