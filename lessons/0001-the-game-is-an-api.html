LESSON 1 · SpaceTraders + Elixir · ~15 minutes

The game is an API

Your first round-trip — a request leaves your terminal, the game answers, Elixir hands you the reply. And a real bug story: how one got found, fixed, and locked down so it can't come back.

The bug is real — and already fixed

This lesson is built around a bug that actually shipped in this repo: get_status/0 failed against the live game because the client demanded a "data" wrapper the root endpoint never sends. It's fixed now, and three tests guard it. You won't break anything today — you'll run the round-trip, read the code to see why it used to fail, and meet the guard rails that would catch it if it tried to come back.

The whole trick

You're learning two things at once: the Elixir/Phoenix stack and the game SpaceTraders. Here's the secret — they're the same activity.

SpaceTraders is a headless game: every action you can take — navigate, mine, trade, buy a ship — is an HTTP endpoint on the game's servers. This repo is an Elixir program whose entire job is to make those requests for you. So every line of code you read teaches you the game, and every game concept teaches you why the code is shaped that way.

The game in 90 seconds

  • All game state lives on the game's servers — systems, waypoints, ships, credits. Your code is only a remote control.
  • You are an Agent. You own ships. Ships move between waypoints inside systems.
  • The loop: accept a Contract → navigate → extract or trade → sell → buy a better ship.
  • The universe resets every few weeks (resetDate — you'll see it today).

Full rules: docs.spacetraders.io → Getting started → Game concepts.

The stack in 90 seconds

  • Elixir is a functional language on the Erlang VM. Functions over values — no classes, no mutation-by-default.
  • This repo is a Phoenix app (web framework + LiveView). But today you only need one file: lib/spacetraders/api.ex, the thin client that talks to the game.
  • mix is Elixir's project tool. mix run executes code inside the project's world.

The five Elixir ideas you need to read the client

  1. A module is a drawer of functions. defmodule SpaceTraders.API do … end
  2. A function returns its last expression. def get_status do request(:get, "/", nil, as: :raw) end
  3. Tuples are little ordered groups: {:ok, value}, {:error, reason}.
  4. Pattern matching assigns by shape. {:ok, data} = result only succeeds if result is a 2-tuple starting with :ok. This is also how functions choose which clause runs.
  5. {:ok, _} / {:error, _} is Elixir's "worked / didn't" convention. Every API function returns one of these.

Run it — the round-trip

Fire up the project's shell (puts the pinned Elixir on your PATH), then call the client's simplest function — the one that asks the game "are you up?":

source scripts/_toolchain.sh
mix run -e 'IO.inspect(SpaceTraders.API.get_status())'
Expected: it works

You should see {:ok, %{"status" => "SpaceTraders is currently online…", "version" => "v2.3.0", …}} — the live game answering your Elixir.

That {:ok, …} is the whole trick: your terminal → Req → https://api.spacetraders.io/v2/ → the game's servers → JSON → an Elixir tuple. It didn't always work — read the code below to see why it used to fail, and how the tests now keep that bug from coming back.

Read the code — how the round-trip is shaped

Open lib/spacetraders/api.ex and follow the breadcrumb trail:

  1. get_status/0 (line 50) asks for the path "/" with as: :raw — "hand me the whole reply, don't try to understand it".
  2. It falls into request/4 (line 259): build the request, send it, then decode the body into whatever as: asked for.
  3. decode/2 for :raw (line 353) is now one honest clause: 
    defp decode(body, :raw) when is_map(body), do: body
    "Any JSON object is fine — pass it through untouched." The when is_map(body) guard just says: only if it's actually a map.
  4. Most endpoints are different. Everything else the client speaks comes wrapped in "data" — see decode_data/2 (lines 355–358), which unwraps {"data": …} before handing the payload to a model's from_json/1.
  5. Now the game's side of the story. Ask the game directly: 
    curl https://api.spacetraders.io/v2/
    The root reply is flat: status, version, resetDate — no data wrapper. The bundled OpenAPI spec confirms it (path /). This endpoint is the one exception to the game's usual {"data": …} envelope.
  6. Where the bug hid. The old :raw clause demanded a "data" key — it copied the envelope logic from the other endpoints without checking whether / actually uses one. It never did. So the client misread a perfectly good reply and returned {:error, "undecodable response: missing `data`"}.

The fix — and the guards that stop a repeat

The fix itself was two small changes. First, make :raw accept the whole body instead of demanding a "data" key — the one-liner you saw at line 353. Second, make the test stub honest.

Here's the interesting part: the original tests were green. The test at client_test.exs stubbed the game to reply with a "data" wrapper — the very lie the buggy code expected. The test passed; production failed. A mock that believes a lie about the API lets the code keep believing it too. That's the bug class, and today it's guarded three ways:

  1. A regression test that speaks the truth. client_test.exs now stubs the real flat shape and asserts get_status/0 decodes it. Break the fix, and this test goes red.
  2. A spec-conformance test. spec_conformance_test.exs loads the bundled OpenAPI spec and checks every endpoint the client speaks against it: root / must stay flat, and all 23 other endpoints must keep their "data" envelope. It runs in every scripts/verify, so a mismatch fails CI.
  3. A live smoke script. scripts/verify-live hits the real game and asserts the client decodes its actual reply. The hermetic test suite never touches the network, so this is the one check that proves it against reality, not against a stub.
Now show that it works
mix test test/spacetraders/api/client_test.exs

Green — and it only stays green because the stub tells the truth. If someone re-adds the old "data" demand, this test and verify-live both fail. That's a guard rail: the bug can't come back silently.

That's the round-trip, end to end: your terminal → Req → https://api.spacetraders.io/v2/ → the game's servers → JSON → an Elixir tuple — plus a lesson in why tests must believe reality, not a convenient story.

Check yourself

1. Where is the game state kept?

SpaceTraders is headless: every system, waypoint, ship and credit balance lives on the game's servers. Your app is only a remote control.

2. Every SpaceTraders game action is…

Navigate, extract, sell, buy — each is an HTTP endpoint on api.spacetraders.io. The Elixir functions in api.ex are just wrappers around those requests.

3. SpaceTraders.API.get_status/0 returns…

Every API function returns {:ok, decoded} or {:error, reason} — Elixir's worked/didn't convention. The decoding already happened inside.

4. The root endpoint GET / is special because…

The game wraps almost every reply in {"data": …} — but the root status endpoint is the exception: flat. The bug was a decoder that assumed the wrapper everywhere.
