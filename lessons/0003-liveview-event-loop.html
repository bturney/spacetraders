Lesson 3 / 30 minutes / LiveView

The LiveView event loop

A LiveView keeps the page's working state on the server. The browser sends it an event; the server sends back only the HTML that changed.

1. Start with the picture

When an Operator clicks Extract, the browser does not call the SpaceTraders game directly. It sends a small event to the running DashboardLive process on this server.

Browser: Operator clicks Extract
    |
    | event name: "extract"
    | Ship symbol: "ORBITALIST-1"
    v
Server: one DashboardLive process
    |
    | asks the Fleet context to extract resources
    v
Fleet.extract_resources(agent, ship_symbol)
    |
    | returns updated information
    v
DashboardLive: renders changed HTML
    |
    v
Browser: updates the relevant part of the page

A context is the application's module boundary for a domain area. Here, Fleet owns Ship actions. DashboardLive owns browser interaction and display.

2. The LiveView has a working notebook

Each open dashboard page has a LiveView process on the server. Its socket is its working notebook: it holds the data needed to render that one page, such as the current Operator and Fleet overview.

Do not confuse this socket with a network socket. For this lesson, read it as “the LiveView's current page data”.

before click: socket has current Fleet overview
after click:  socket has refreshed Fleet overview

LiveView compares the two renders and sends the browser a small update.

This is why the dashboard can update without a full browser reload.

3. A browser event goes to handle_event

The real dashboard has a function named handle_event. The name tells Phoenix LiveView what it is for: handle an event sent by the browser.

Browser click: phx-click="extract"
    |
    v
DashboardLive.handle_event("extract", %{ "symbol" => ship_symbol }, socket)
    |
    v
Fleet.extract_resources(agent, ship_symbol)
    |
    v
refresh_agent_fleet(socket, agent.id)
    |
    v
{:noreply, updated_socket} -> HTML patch to browser

The handler is at lib/spacetraders_web/live/dashboard_live.ex:390. Read it only as: “on Extract, ask Fleet to do the work, refresh page data, and update the browser.”

4. A Ship process can also update the page

Not every dashboard update starts with a browser click. A ShipServer sends a message when a Ship's Arrival or Cooldown changes. The dashboard receives that kind of message in handle_info.

ShipServer finishes a timer
    |
    | broadcasts: {:ship_updated, agent_id, ship_symbol}
    v
DashboardLive.handle_info(...)
    |
    | refreshes page data
    v
Browser receives updated HTML

The real callback is deliberately small:

def handle_info({:ship_updated, agent_id, _ship_symbol}, socket) do
  {:noreply, refresh_agent_fleet(socket, agent_id)}
end

_ship_symbol means this message contains a Ship symbol, but this function does not need it. The updated socket causes LiveView to update the page.

Practice: name the source

For each situation, say which function receives it:

  1. An Operator clicks Extract.
  2. A Ship finishes an Arrival timer.

Answers: handle_event receives the browser click. handle_info receives the Ship update. Verify at lines 390 and 1433 of dashboard_live.ex.

An Operator clicks a dashboard button. Which callback receives it?

handle_event/3 receives browser events. handle_info/2 receives messages from inside the application, such as a ShipServer update.

Before moving on

Remember only this: browser click means handle_event; message from another application process means handle_info. A later lesson can add the with and pipeline syntax one piece at a time.
